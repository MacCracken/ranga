# P(-1) review — 2026-11-02 (2.1.2)

**Scope.** This review closes out the toolchain bumps from 2.0.3 to 2.1.1: cyrius
6.6.9 → 6.7.18, plus the dependency moves that came with them.
- prakash 2.2.8 → 2.15.1;
- ai-hwaccel 2.3.18 → 2.5.6;
- mabda 4.1.1 → 4.2.0;
- hisab, samvada, chitra and sakshi.

The question it answers: **what did the bumps change in ranga's behaviour, and what
did they leave behind?** That covers:
- regressions;
- workarounds the toolchain has outgrown;
- warnings;
- comments that now state false facts;
- stale tooling.

This is ranga's first filed audit. The port's fidelity against Rust 1.0.1, the 25 items
the [2026-11-02 parity review](../development/parity-rust-v-cyrius.md) found, is
**not** in scope except where a bump caused it. Those items are sequenced in the
[roadmap](../development/roadmap.md) (2.2.x).

**Method.** The P(-1) steps, in order:
1. **Cleanliness.** `cyrius fmt --check`, `cyrius lint --strict --strict-deferrals` and
   `cyrius vet` over all of `src/` and `tests/`, then the full suite.
2. **Benchmark baseline.** `scripts/bench-history.sh` at 2.1.1, after rewriting it.
   The first rows of `bench-history.csv` are this baseline.
3. **Cross-toolchain diff.** 15 probe programs built twice and run on identical
   inputs:
   - against the 2.0.3 tree under cyrius 6.6.9;
   - against the current tree under 6.7.18.

   About 560,000 output values were compared byte for byte, covering color, convert,
   pixel, filter, transform, histogram, blend, composite and ICC. Where the outputs
   differed, both sides were also compared against the Rust 1.0.1 crate built with
   `cargo --release`.
4. **Targeted review** of what the bump notes say changed:
   - every `fl_alloc` / `fl_calloc` site with a computed size (6.6.7 made size 0
     return 0);
   - a name-collision scan of `src/` against every vendored `lib/` file (6.7.18
     refuses a `var` that reuses a top-level const);
   - each boundary behaviour the `error.cyr` shims exist for, probed again at 6.7.18;
   - every comment that states a toolchain or dependency fact.
5. **Repairs.** One at a time. Each behavioural fix has a test that **fails on 2.1.1**,
   and the suite ran after each.
6. **Post-repair benchmarks**, and a re-run of the 15 probes.

**Result.** 9 findings, none critical or high: 2 medium, 4 low, 3 info. Eight are fixed
in 2.1.2. Finding I, an upstream dependency's warning, is recorded only.

## What the bumps changed: the cross-toolchain diff

Across 15 probes, **13 produce byte-identical output under 6.6.9 and 6.7.18.**
Every SUSPECT item in the parity review therefore predates the bumps, the f32/f64
paths and `affine_inverse` included. Two probes moved:

- **`gradient_linear_angled` at 1e25° now matches Rust.** Under 6.6.9 the whole
  37×23 image for that angle differed from Rust: 3,403 of 3,404 bytes. Under 6.7.18
  it is byte-identical. The probe's other 20 angles were identical under both. The
  toolchain's f32/f64 cosine now reduces huge arguments. The bump fixed this, and
  no ranga change was involved.
- **ICC `pow`-based results moved by 1–2 ULP, net toward Rust.**

  | | Values differing from Rust |
  | --- | ---: |
  | 6.6.9 | 11,273 bytes |
  | 6.7.18 | 2,738 bytes |

  9,983 bytes were fixed and 1,448 bytes that had matched now differ, all in the
  gamma, matrix and para paths and all ≤ 2 ULP. LUT, table and profile-byte outputs
  did not move. This is ganita's `pow` changing between stdlib snapshots. It is not a
  defect, but it means **f64 results through `pow` are not stable across pins**.
  Only exact-match tests on those paths would notice.

GPU output was not part of this diff. All five GPU suites pass on hardware (AMD
Cezanne) under mabda 4.2.0, with byte-exact expected values.

## A — mft2 with zero input entries was rejected (medium)

Since cyrius 6.6.7, `fl_alloc(0)` returns 0 (before that it returned a 16-byte block).
So `_icc_lut_build`'s `fl_alloc(in_entries * 8)` failed for `in_entries == 0`, and the
parser returned `RG_ERR_ALLOCATION`. Rust parses such a profile and keeps empty
curves, which `apply_curve` treats as identity (`rust-old/src/icc.rs:376-378`).
ranga's `_icc_apply_curve` already treated `n == 0` as identity, so the allocation
was the only thing in the way. ranga first pinned a toolchain with this behaviour at
2.0.3 (6.6.9).

**Fix.** An empty curve is not allocated. Its slot stays null from the profile's
`fl_calloc`, and `icc_lut_profile_free` already skips null curves.

**Test** (`tests/icc.tcyr`, "mft2 with ZERO input-table entries"). The same asymmetric
2×2×2 CLUT is built with zero entries. The profile now parses, its curve length is
0, and pure red, half red and quarter blue pass through unchanged into the grid. On
2.1.1 the parse failed with -6.

## B — huge finite angles became NaN (medium)

`_rg_sin`/`_rg_cos` returned NaN for |x| ≥ 2^63. That guard was right when x86
`fsin`/`fcos` returned the argument unchanged there. At the 6.7.18 pin,
`f64_sin`/`f64_cos` reduce every finite argument and match glibc bit for bit (checked
at 1e20, 3.02e23, 1.57e60 and `f64::MAX`), and glibc is what Rust's `sin_cos` calls.
So the guard had become a divergence:
- `affine_rotate(1e20)` was an all-NaN matrix, where Rust's is finite;
- `oklch_to_oklab` and the CIEDE2000 terms route through the same shims.

The parity review classed `affine_rotate` as PARITY with a documented NaN. That
documentation described a toolchain that no longer exists.

**Fix.** The guard is now "not finite": NaN in, or ±inf in, gives NaN out, which is
what Rust returns too. Every finite angle is delegated.

**Tests.**
- `tests/ranga.tcyr`: `sin(1e20)` and `cos(1e20)` equal glibc's bits; NaN still gives
  NaN.
- `tests/transform.tcyr`: `affine_rotate(1e20)`'s a and b equal glibc's
  `cos(1e20)` and `sin(1e20)`.

All four new assertions returned NaN on 2.1.1.

## C — zero-tag profile reported as an allocation failure (low)

This is the same 6.6.7 change, at `_icc_parse_tag_table`'s
`fl_calloc(count * 24)`. Rust parses the empty table and then fails the first tag
lookup with `InvalidFormat`, from both `IccProfile::from_bytes` and
`IccLutProfile::from_bytes`. The port reported `RG_ERR_ALLOCATION`, which a caller
would read as out-of-memory rather than a bad file. ICC is the module that parses
untrusted input.

**Fix.** An empty table gets one zeroed entry, which no signature matches, so the
lookup fails and returns `RG_ERR_INVALID_FORMAT` as in Rust.

**Test** (`tests/icc.tcyr`, "A tag count of ZERO"). Both parsers now reject the sRGB
fixture with its count set to 0 as `RG_ERR_INVALID_FORMAT`. On 2.1.1 both returned -6.

**Every other computed-size allocation was checked and is safe.** Each one is
guarded, or its size cannot reach 0:
- `bytevec`'s `cap > 0` / `n > 0`;
- `buffer_pool_new`'s `max_buffers > 0`;
- the luma scratch's `pairs > 0`;
- `lut3d_new`'s `size < 2` rejection;
- `flood_fill`'s seed bounds;
- kernel lengths of `2r+1`;
- headers added to every histogram allocation.

## D — the ColorBurn warning (low)

`return one - ganita_f32_min(...)`. The callee is declared `: i64` and returns f32
bits, and cyrius 6.6.10 started warning about f32 arithmetic with a non-f32 operand.
The value was right, because the compiler passed the bits through, but only for that
reason. The cyrius 6.6.10 downstream survey had named this exact line.

**Fix.** `_bl_sub(one, ganita_f32_min(...))`. The helper's typed parameters make the
subtract an f32 subtract explicitly.

**Verified.** The suite passes, and the exhaustive probe is still byte-identical to
Rust: all 12 modes × all 65,536 channel pairs, 1,994,032 bytes.

## E — the bench script was Rust (low)

`scripts/bench-history.sh` ran `cargo bench` and wrote `benches/history.csv`. Neither
exists in this tree, so the script failed on every run, and no Cyrius benchmark had
ever been recorded. `version-bump.sh` had the same problem and was fixed at 2.0.2.

**Fix.** The script was rewritten on prakash's pattern. It runs `cyrius bench
tests/ranga.bcyr`, normalises each row to ns, and appends to `bench-history.csv`. Each
row records the version, the commit, the cyrius pin and the timer-floor regime,
because rows from different instruments are not comparable.

**Benchmarks.** Before and after are both in `bench-history.csv`, rows marked 2.1.1
and 2.1.2. 34 of 35 are within ±10%, and the median ratio is 1.01.
- The outlier is `noise_gaussian_1080p` at 1.17×. That bench runs a single iteration,
  its code did not change, and three runs of identical noise code measured 1.25 s,
  470 ms and 552 ms.
- No repair touched a hot path.

## F — the CI lint gate (low)

The Lint step's comment said "`cyrius lint` takes ONE path and ALWAYS exits 0". Both
claims are false since cyrius 6.6.5: `lint` takes 1..N files, and `--strict` /
`--strict-deferrals` exit non-zero. The step looped over every file and parsed the
printed totals, which only worked while those strings never changed.

**Fix.** One call: `cyrius lint --strict --strict-deferrals src/*.cyr tests/*.tcyr`.
It was checked at the pin on scratch files mixed with clean ones:
- a file with a warning makes it exit 2;
- a file with an untracked deferral makes it exit 2;
- the repository gives exit 0;
- the plain form exits 0 in every case.

## G — discarded `#must_use` results (info)

`tests/icc.tcyr:70-74` called `_icc_read_u32_be` / `_icc_read_u16_be` for their error
code and dropped the value, which produced three compiler warnings. Those calls now
assert that a rejected read returns 0, a stronger test than before.

## H — comments the bumps made false (info)

None of these changes code, but each told a reader something untrue about the current
toolchain:

- **`error.cyr`:** the shim table said `ganita_f64_pow(0, 2)` and `f64_exp(±inf)`
  return NaN. At 6.7.18 they return Rust's values; that was probed. The shims stay,
  redundant, because they state the contract. The trig note is covered by B.
- **`composite.cyr`, NaN:** ganita's `f32_min`/`max` ordered NaN high. Since ganita
  1.2.x they ignore it, as Rust's do. The radial gradient's explicit NaN check is
  now redundant and kept, and the clamp-side check is still needed.
- **`composite.cyr`, cosine:** `f64_cos` was described as undefined past 2^63.
  See the cross-toolchain diff.
- **`transform.cyr`:** the rotate comment. See B.
- **`pixel.cyr`:** said `#derive(Serialize)` on an enum emits no codec. At 6.7.18 it
  works and writes the variant name (`"Dark"`), which is serde's own wire form. That
  changes the 2.4.x serde decision.
- **`spectral.cyr`:** said every re-export keeps its prakash name. Three are renamed
  at prakash 2.15.1 (`cie_1931_table()`, `spec_visible_min_nm()`,
  `spec_visible_max_nm()`), and `VISIBLE_MAX_NM` was missing from the list.
- **`hwaccel.cyr` and `gpu_context.cyr`:** headers named ai-hwaccel 2.3.17 and mabda
  4.0.9. They now point at the pin in `cyrius.cyml`.
- **`gpu_pipeline.cyr`, `gpu_spirv.cyr` and `gpu_kernels.cyr`:** they described
  mabda's lowerer as of 4.0.x:
  - no loops;
  - no `OpFDiv`;
  - no `OpSelect`;
  - no `ULessThan`;
  - register pressure on bilinear;
  - four ops "work on the wgpu path".

  mabda 4.1.0 / 4.2.0 lifted the first four, the bilinear failure is the 256-id cap,
  and nothing dispatches WGSL. The comments now state this and point at
  [architecture note 001](../architecture/001-mabda-native-gpu-constraints.md). The
  workarounds themselves are retired in roadmap 2.5.x.
- **`simd_u8.cyr`:** the in-tree `hashmap_fast.cyr` reference, since that file was
  removed in 2.1.1. The comment now names the stdlib's copy.

## I — prakash's warnings (info, upstream)

Every compile that includes `lib/prakash.cyr` prints three warnings:
- `undefined function 'num_fft'`. prakash's `wave_pattern` references hisab, which
  this bridge does not include. `distlib` reports the same name as "still undefined"
  for `ranga-spectral.cyr`, so a consumer of that bundle must supply it.
- Two "comparison mixes f64 and integer operands" warnings.

These are prakash's to fix, and ranga does not modify vendored `lib/`. With D and G
fixed, **ranga's own code compiles with zero warnings.**

  (1,921 + 18 new, each of which failed on 2.1.1).
- **Lint and formatting:** strict lint and `fmt --check` are clean on all 41 files.
- **Dependencies:** `cyrius deps --verify` passes 69/69, and the 7 commit pins match

- **Bundles:** `distlib --check` is current on all four bundles.
- **No side effects:** the 15 probes give the same bytes before and after the repairs.
  So A–D changed only the cases they target.
